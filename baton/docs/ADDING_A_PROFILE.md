# Baton Talkに人物プロフィールを追加する手順（必読）

> セッションをまたぐ引き継ぎ（本番ブランチ・過去の事故・Ownerのデザインの好み・作業履歴）は
> [`SESSION_HANDOFF.md`](./SESSION_HANDOFF.md) にある。作業前にそちらも読むこと。

このドキュメントは、`/profile/<slug>/` に新しい人物プロフィールを追加する
ときのための、事故を防ぐための固定手順とテンプレートです。
**新しいチャット・新しいセッションで作業を頼まれたら、何よりも先にこれを
読むこと。**

## 誰が何をやるか（3者の役割分担）

unveil（古谷祐麻氏）追加のときに、この役割分担が曖昧だったために
のべ十数時間かかった。今後は必ずこの3者体制で進める。

| 担当 | やること | やらないこと |
|---|---|---|
| **このチャット（Claude Code / リポジトリ側）** | `src/data/profiles.ts` 等サイト側コードの追加、`gas/Code.gs` の**コード内容**の作成・修正、git commit/push、ビルド確認、デザインプレビューの用意 | **Google側の画面操作は一切できない**（script.google.comへの通信がこの環境からブロックされている）。GASへの貼り付け・デプロイ・実行は物理的に不可能 |
| **Owner（ユーザー）** | 掲載する本人の実名・会社名・肩書き・実在するURL・**受信用メールアドレス**（本物 or 一時テスト用）の提供、デザインの承認、本番pushの許可 | コードは書かない。GAS操作はClaude in Chromeに渡す |
| **Claude in Chrome（ブラウザ拡張）** | 実際のGoogle画面を見ながらの、GASコードの貼り付け・`BATON_PROFILES`編集・デプロイ管理・関数実行・本番サイトでのフォーム送信テスト | サイト側のコード（このリポジトリ）は触らない。指示された1プロジェクト以外は触らない |

**このチャットからGASの状態を直接確認する手段はない。** 「デプロイした」
「動くはず」は口約束にしかならないので、必ずClaude in Chromeに
実機で最後まで確認させ、結果（実行ログ・実サイトでの送信結果）を
報告してもらってから完了とする。

## 手順

### 1. サイト側（このリポジトリ。このチャットが担当）

1. `src/data/profiles.ts` に、下記テンプレートをコピーして1件追加する
2. `profile/<slug>/index.html` を `profile/kabeya/index.html` からコピーし、
   `<script>` の参照先だけ `/src/entries/profile-<slug>.ts` に変える
3. `src/entries/profile-<slug>.ts` を1行で作る
   （`import { mountProfilePage } from '../profile/main'; mountProfilePage('<slug>');`）
4. `vite.config.ts` は `profiles` 配列から自動生成されるので触らない
5. `npm run build` で型チェック・ビルドが通ることを確認する
6. push前に必ず production ブランチ（`claude/baton-backend-implementation-zu0h6k`）
   を fetch し、他セッション/Ownerの直接コミットで進んでいないか確認してから
   マージ・pushする（このブランチは複数の作業者が同時に触っている）

#### `src/data/profiles.ts` テンプレート

```ts
const exampleProfile: TalkProfile = {
  id: 'example',
  slug: 'example',
  name: '姓 名',
  company: '会社名',
  title: '役職（例: 代表取締役CEO）',
  tagline: '一行のキャッチコピー（未指定なら簡易ヒーローになる）',
  bio: '人物紹介の一段落。経歴・現在の肩書きなど。',
  business: [
    '事業内容の説明。段落ごとに配列の要素を分ける。',
  ],
  services: [
    { name: 'サービス名', description: '一行説明' },
  ],
  media: [
    { label: '公式サイト', url: 'https://example.com/' },
    // image は任意。実際に確認できた画像URL以外は入れない
  ],
  listSummary: '一覧ページ用の一行説明（未指定ならtaglineで代用）',
  businessTags: ['事業タグ1', '事業タグ2', '事業タグ3'], // /profile/ 一覧の右側。最大3件
  keywordTags: ['キーワード1', 'キーワード2', 'キーワード3'], // 同上。最大3件
  photo: { src: '/profile-______.webp', alt: '姓 名', caption: 'OSAKA / JAPAN · 2026' }, // 任意
  theme: { primary: '#______', accent: '#______', bg: '#______', text: '#______' },
  active: true, // false にすると /profile/ 一覧に出ない（GAS側もactive:falseにしておく）
};

export const profiles: TalkProfile[] = [kabeyaProfile, unveilProfile, exampleProfile];
```

#### 一覧ページ（/profile/）の表示ルール（要指摘・要注意）

`listSummary` と `businessTags` / `keywordTags` は、`/profile/` の一覧で
1行のカードとして並ぶ。unveil追加時に実際に指摘された点なので、
新しいプロフィールを追加するたびに必ず確認すること。

- **`listSummary` は必ず1行に収まる短さにする。** 目安は20〜24文字程度。
  「〜を横断して伴走する〜代表」のような説明的な長文にしない。
  例: ◎「ブランディング・Web制作・採用支援」 ✕「ブランディング・Web制作・
  採用支援を横断して伴走するunveil代表」（2行になって見栄えが悪い）
- **`businessTags`（上段）と `keywordTags`（下段）は、絶対に内容を
  被らせない。** 上段＝事業领域そのもの（3つ）、下段＝それとは別の
  切り口の強み・特徴キーワード（3つ）にする。
  例: ◎ 上段「ブランディング/Web制作/プロダクト開発」・
  下段「世界観の設計/徹底ヒアリング/SEO対策」
  ✕ 上段「ブランディング/Web制作/採用支援」・下段「ブランディング/Web/
  クリエイティブ」（同じ言葉の言い換えを繰り返しているだけ）
- 各タグは日本語で6〜7文字程度まで（英数字が混ざるとやや余裕ができる）。
  それより長いとカードの枠内で見切れる。長い表現は短い言い換えを探す。

**絶対に入れてはいけない情報**: 資本金、従業員数、売上、その他の企業スペック
（IR的な数値）。実績として触れたい場合は `bio` / `business` の文章の中で
自然に触れる程度にとどめ、`stats` のような独立した数値バッジ・カードには
絶対にしない。

**URLについて**: `media` に入れるリンクは、必ず本人・Owner・信頼できる
一次情報源から得た実在のURLだけを使う。似た名前の別会社・別ドメインが
存在することがあるため、確信が持てないURLは絶対に推測で入れず、
Ownerに確認すること。

#### デザインは1つ。変えるのは「色」と「中身」だけ

**プロフィールページのデザインは全員共通のテンプレート1つである。**
レイアウト・ロゴ・グラフィック・モーション・WebGLは、掲載者ごとに作り分けない。
`profiles.ts` に1件足せば、壁谷プロフィールと同じ構成のページが出来上がる。

人ごとに変わるのは次の2つだけ。

1. **色** — `theme` の4色
2. **中身** — `name` / `title` / `tagline` / `bio` / `business` / `services` / `media` / `photo`

`heroVariant` は指定しない（既定がテンプレート）。`heavyWebGL` も `monument` も
**新規プロフィールでは使わない**。どちらも過去の名残で、今は指定しなくても
テンプレートのWebGLヒーローが付く。

##### theme の4色の決め方

| キー | 役割 | 注意 |
|---|---|---|
| `primary` | **その人の色。** 罫・ラベル・ボタン・立体の基調 | ボタンは白抜き文字なので、**白に対して読める濃さ**にする |
| `accent` | 差し色。立体を波が通るときに灯る色、グラデーション | `primary` と同系で一段明るい色が収まりやすい |
| `bg` | 地の色 | ここが暗いか明るいかで、後述の切り替えが自動で起きる |
| `text` | 本文の色 | `bg` に対して十分な明度差を取る |

`bg` の明度は `vite.config.ts` が判定する。暗ければ body に `profile--dark` が付き、
カード・入力欄・フッターなど白地前提の共通部品がまとめて暗色側へ寄る。
WebGLの立体も、明るい地では加算合成をやめて通常合成に切り替わる。
**つまり `bg` を明るい色にするだけで、同じテンプレートの明るい版になる。**

実例:

- kabeya … `primary: '#C8102E'`（赤） / `bg: '#0A0A0C'`（黒） → 暗色版
- unveil … `primary: '#8A6338'`（ブロンズ） / `bg: '#F2EEE6'`（アイボリー） → 明色版

##### 写真

`photo` は任意。置かない、または読み込みに失敗したときは、額の中に
**姓の頭文字**が出るフォールバックに戻るので、写真が揃う前でもページは成立する。
画像は `public/` 直下に置き、`src` はそこからの絶対パスで書く。

## 申請できる人を制限する（申請許可リスト）

Batonが検索エンジンに載って以降、プロフィールURLさえ知っていれば
無関係な第三者でも「話したい」の申請フォームを送信できてしまう
（プロフィール自体には申請者側の制限が一切なかった）。これを防ぐため、
`gas/Code.gs` に**申請許可リスト**というメールアドレスの許可制ゲートを
入れてある。

- 対象スプレッドシート（`BATON_SPREADSHEET_ID` ＝「LINE会話ログ」）の中に、
  `申請許可リスト` という名前のシートを自動生成する
  （`setupBatonSheets` 実行時、または初回の申請時に無ければ作られる）。
- 列は `メール / 備考 / 登録日`。**A列（メール）に、申請してよい人の
  メールアドレスを1行1件で入れるだけ**で運用できる。大文字・小文字は
  区別しない。全プロフィール共通の1枚のリストで、プロフィールごとには
  分けていない（例: このリストに載っていれば、壁谷にもunveilにも申請できる）。
- リストに無いメールアドレスで申請すると、`batonSubmitTalk` が
  `{ ok:false, error:'not_allowed', message:'このメールアドレスでは、
  現在お申し込みいただけません。' }` を返し、送信自体を拒否する
  （フォーム側は追加のコード変更なしで、この `message` をそのままエラー
  表示に出す）。
- **コードの再デプロイは不要。** Ownerがスプレッドシートの行を
  追加・削除するだけで「申請できる人」を増減できる。
- 既存のスプレッドシートに、たまたま別名のタブを用意していた場合は、
  そのタブ名を `申請許可リスト` に変更するか、中身（メールアドレス）を
  このシートに移すこと。シート名が一致しないと、コードは自動的に
  新しい空のシートを別途作ってしまう。
