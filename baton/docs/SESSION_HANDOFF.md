## 2. プロフィールの作り方

**デザインは全員共通のテンプレート1つ。人ごとに変えるのは「色」と「中身」だけ。**

1. `baton/src/data/profiles.ts` の `profiles` 配列に1件足す
2. `baton/profile/<slug>/index.html` を `profile/kabeya/index.html` からコピーし、`<script>` の参照先だけ変える（body のクラスは触らない。vite が自動で付ける）
3. `baton/src/entries/profile-<slug>.ts` を2行で作る
4. `baton/` で `npm ci && npm run build`（型チェックも走る）
5. `gas/Code.gs` の `BATON_PROFILES` に1件足す（`recipientEmail` が本物になるまで `active: false`）
6. 作業ブランチ → PR → 本番ブランチへマージ

`vite.config.ts` のエントリ一覧は `profiles` 配列から自動生成されるので触らない。

### theme の4色

| キー | 役割 | 注意 |
|---|---|---|
| `primary` | **その人の色。** 罫・ラベル・ボタン・立体の基調 | ボタンは白抜き文字。**白に対して読める濃さ**にする |
| `accent` | 差し色。立体を波が通るときに灯る色 | `primary` と同系で一段明るい色 |
| `bg` | 地の色 | **ここの明度で暗色版／明色版が自動で切り替わる** |
| `text` | 本文の色 | `bg` に対して十分な明度差 |

`bg` が暗いと `vite.config.ts` の `isDarkTheme` が判定して body に `profile--dark` が付く。
これでカード・入力欄・フッターが暗色側へ寄り、ヒーローのWebGLも加算合成→通常合成に切り替わる。

- kabeya … `primary #C8102E`（赤） / `bg #0A0A0C`（黒） → 暗色版
- unveil … `primary #8A6338`（ブロンズ） / `bg #F2EEE6`（アイボリー） → 明色版

### 指定してはいけないもの

`heavyWebGL` / `monument` / `heroVariant` は過去の名残。**新規プロフィールでは指定しない。**
指定しなければテンプレートのWebGLヒーローが付く。

### 写真

`photo` は任意。`public/` 直下に置き、`src` はそこからの絶対パス（例: `/profile-kabeya.webp`）。
未配置・読み込み失敗のときは額の中に姓の頭文字が出るので、写真が揃う前でもページは成立する。

## 4. 本番へ出す手順と、本番かどうかの見分け方

1. 作業ブランチを**本番ブランチから**切る
2. PR を本番ブランチ宛てに出す
3. `Cloudflare Pages: baton` のチェックが **success** なら通る
4. マージする
5. マージコミットの `Cloudflare Pages: baton` チェックを見る

**本番デプロイの見分け方**: Cloudflare のチェック本文に **「Branch Preview URL」の行が無ければ本番デプロイ**。あればプレビュー。

```bash
curl -sS "https://api.github.com/repos/MusicJapanLLC/test/commits/<sha>/check-runs"
```

`music-japan` と `second-take` のチェック失敗は**別プロジェクトの既存問題**。baton とは無関係なので、それを理由に止まらない。

## 5. ハマりどころ（事故と対処）

### ① 土台のブランチを間違えた（最重要）

既定ブランチにある `baton/` は6サービス版の古い別物。また `chatgpt/baton-seo-aio-production-20260914` は名前に production と付いているが**本番ではない**。
これらを土台に作ったため、本文も構成も実在のページと全く違うものが出来上がった。

→ 作業前に必ず `claude/baton-backend-implementation-zu0h6k` を土台にする。**ブランチ名の "production" を信用しない。**

### ② マージしたのに本番が変わらない

GitHub上の「Vercel – baton: Deployment has completed」を本番反映だと誤認した。実際はPreviewで、配信元は Cloudflare Pages だった。

→ 判定方法は「4.」のとおり。DNSを引くと Cloudflare のIP（104.21.x / 172.67.x）に向いていることでも確認できる。

### ③ 本番ページの内容が取得できない

実行環境は egress proxy で `baton.music-japan.com` も `*.pages.dev` も 403。本番の見た目を直接確認できない。

→ 本番ブランチをローカルで `npm run build` → `vite preview` → ブラウザ（Playwright）で実際に開いて確認する。**「反映されました」と断定しない。**

### ④ 明るいテーマだけ白い箱が浮いた

`service.css` が白地サービスページ向けで、カード・入力欄の地を `#fff` で直に敷いている。暗色側だけ上書きしていたため明るいテーマで白が出た。

→ 面の色は theme から作る（`--surface` / `--field` / `--hairline`）。**共通部品に白や黒を直書きしない。** 新しい色のプロフィールを足したらフォームまで目視確認する。

### ⑤ WebGLが白地で見えなくなる

加算合成は白地だと色が飛ぶ。→ `scene-hero.ts` の `isLightBg` で判定し、明るい地では通常合成に切り替える（実装済み）。

### ⑥ 他セッションと同じブランチを同時に触る

本番ブランチは他のClaudeセッションも触っている。作業中にブランチが進むことがある。

→ 作業前と push 前に必ず `git fetch`、必要ならリベース。本番ブランチへ直接 push せず、作業ブランチ → PR → マージを守る。

### ⑦ GASで別の関数を実行した（過去の事故）

6サービス用の `setupSheets` を実行し、Ownerの業務スプレッドシート（LINE会話ログ）に無関係な6シートが作られた。

→ 実行するのは `setupBatonSheets` のみ。「LINE会話ログ」スプレッドシートの拡張機能→Apps Script は絶対に開かない。
