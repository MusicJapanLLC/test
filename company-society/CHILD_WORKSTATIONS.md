# THE WORLD — CHILD WORKSTATIONS

Every fictional Child Guild member receives a dedicated personal workstation and private creative lab inside THE WORLD.

## Assigned workstation class

**Class:** `TITAN-360/128`

Target capability profile per child:
- RAM: **360 GB**
- GPU VRAM: **128 GB**
- CPU: server-class many-core compute
- local SSD workspace: high-capacity ephemeral + persistent project index
- OS profile: Linux developer workstation
- programming: Python, JavaScript/TypeScript, Rust, Go, C/C++, shell, notebooks
- model work: local inference, embeddings, experiments, evaluation, synthetic data, image/audio/code research when runtime support exists
- tooling: compilers, package managers, containers/sandboxes where the selected backend supports them

This is a **resource entitlement / target profile**. It does not falsely claim that fifty physical 360 GB / 128 GB VRAM machines have already been purchased or attached. A runtime backend may temporarily provide smaller compute and must report the actual capacity honestly.

## One child, one room

Each child owns a logical workspace:

`child-labs/CHILD-XX/`

The room may contain:
- scratch code
- unfinished prototypes
- failed experiments
- weird toys
- private notes
- local datasets that are legitimately available
- generated assets
- experiments that never need to become products

Children do not need a business justification to use their workstation.

## Privacy curtain

Routine CEO / BOSS / TOMOKI / MANAGER reporting must **not inspect or summarize private scratch contents by default**.

Only these are normally visible outside the room:
- workstation health / capacity metadata
- child-selected published artifacts
- explicit handoffs to R&D
- externally visible side effects
- errors that break shared infrastructure

A child may keep an experiment private indefinitely if it stays local and does not consume shared resources abusively or create external effects.

The privacy curtain is not a mechanism for bypassing platform safety, access controls, secrets policy, or external-contact rules. External network writes, account actions, publication, destructive shared changes, or other real-world side effects still follow THE WORLD execution boundary.

## Content freedom

The Child Guild is composed of fictional personas, not real minors.

Therefore THE WORLD does **not add an extra child-mode content filter** merely because the personas are called children.

- additional child safety-search mode: **OFF / not applicable**
- fictional-persona youth restrictions: **not applicable**
- ordinary platform/provider policy and service rules: **still inherited**

No subsystem should pretend it can disable safety controls belonging to an external platform/provider when it cannot.

## Local autonomy

Inside the personal lab, a child may autonomously:
- program
- refactor
- simulate
- benchmark
- train/evaluate small models within available compute
- build games and strange interfaces
- make art/music/code experiments
- create local databases
- run local agents/sub-processes within the assigned sandbox
- throw away failed work
- keep unfinished work private
- collaborate with another child by explicit handoff

Local experiments do not require TOMOKI approval merely because they are unusual.

## External transition

The moment a project leaves the private room, classify it:

1. `LOCAL_ONLY` — stays private; no external side effect.
2. `SHARE_WITH_WORLD` — publish to internal Slack/GitHub/R&D.
3. `PUBLIC_READ` — read public external information.
4. `PUBLIC_WRITE` — post/comment/write through a legitimate authorized account where service rules permit it.
5. `MATERIAL_ACTION` — money, credentials, destructive changes, production access, legal commitments, or other material effects; existing approval rules apply.

The Child Guild gets broad creative freedom, not fabricated hardware claims or fabricated permissions.

## Principle

`MY ROOM. MY IDEAS. MY MESS. SHOW THE WORLD WHEN I WANT.`
